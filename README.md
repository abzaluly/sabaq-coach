# Orle

Групповые привычки с геймификацией и честной проверкой. Друзья объединяются в группы, ставят себе измеримые привычки, отмечают выполнение с фото, проверяют друг друга и соревнуются за очки. Mobile-first PWA, интерфейс на русском (i18n заложен для казахского и английского).

> **Честно о главном.** Полностью исключить обман в приложении для привычек невозможно: можно сфотографировать чужие отжимания, договориться с другом о подтверждениях или выбрать фото из галереи вместо камеры. Orle делает обман **неудобным, заметным и невыгодным** — см. раздел «Анти-чит».

## Стек и архитектура

- **Next.js 16** (App Router, Server Components, Server Actions) + **TypeScript strict**
- **Supabase**: Auth (email OTP / magic link, SMS OTP через Send SMS Hook), Postgres + RLS, Storage, Realtime, pg_cron
- **Tailwind CSS 4** + компоненты в стиле shadcn/ui, **next-intl**, **Zod**
- **sharp** — обработка фото-пруфов на сервере (удаление EXIF/GPS, WebP, перцептивный хэш)
- **web-push** — пуш-уведомления PWA; email — Resend (или файл в dev)
- **Vitest** (юнит + тесты БД/RLS), **Playwright** (сквозные сценарии на мобильном viewport)

```
Браузер (PWA) ──► Next.js (Vercel)
                   ├─ Server Components / Actions ── supabase-js с cookie-сессией (RLS действует)
                   ├─ /api/checkins      фото → sharp (без EXIF) → Storage (приватный) → register_proof → create_checkin
                   ├─ /api/cron/tick     тик планировщика + рассылка уведомлений (CRON_SECRET)
                   └─ /api/auth/sms-hook Supabase Send SMS Hook → Mobizon/Twilio
Supabase
   ├─ Postgres: клиент ТОЛЬКО ЧИТАЕТ свои группы (RLS); любая запись — SECURITY DEFINER-функции
   ├─ points_ledger — append-only журнал очков с ключами идемпотентности
   ├─ pg_cron → app_private.tick(): решения по отметкам → закрытие периодов → сезоны → очередь уведомлений
   └─ Storage: бакет proofs (приватный), фото выдаются подписанными ссылками только участникам
```

**Главный принцип:** у роли `authenticated` есть только `SELECT` (и запись в собственные настройки уведомлений). Отметки, голоса, очки, статусы, достижения — только через серверные функции, которые сами берут время, проверяют права и инварианты. Тест `tests/db/grants.test.ts` сверяет, какие функции может вызвать клиент, с белым списком.

## Быстрый старт

Нужны Node ≥ 20.9 и pnpm.

### Вариант А — Supabase CLI (Docker)

```bash
pnpm install
pnpm db:start                 # поднимает Supabase, применяет миграции и seed.sql
cp .env.example .env.local    # вставьте anon и service_role ключи из вывода db:start
pnpm dev                      # http://localhost:3000
```

Письма с кодами — в Mailpit: http://localhost:54324.

### Вариант Б — без Docker (локальный стек)

Если Docker недоступен, `scripts/local-stack` поднимает совместимый стек поверх вашего Postgres ≥ 15: **GoTrue** (Supabase Auth) и **PostgREST** (скачиваются бинарники), мини-шлюз `/auth/v1`, `/rest/v1`, `/storage/v1`, эмулятор Storage и SMTP-ловушку.

```bash
pnpm install
PGURL=postgres://postgres:postgres@127.0.0.1:5432/postgres pnpm stack:setup   # БД orle_dev + .env.local
pnpm stack:start
pnpm dev
```

Последнее письмо: `http://localhost:54324/latest?to=<email>` (поле `code`). SMS с кодом — в `.local-stack/sms/<номер>.json`. Realtime в этом стеке нет — лента просто обновляется при переходах.

## Тесты

```bash
pnpm test          # Vitest: юнит + тесты БД (≈135 тестов)
pnpm test:e2e      # Playwright, Pixel 7; с E2E_BACKEND=1 — полные сценарии против Supabase
pnpm lint && pnpm typecheck
pnpm load-test     # нагрузочная проверка (см. «Производительность»)
```

**Тесты БД** работают на любом Postgres ≥ 15 (по умолчанию `postgres://postgres:postgres@127.0.0.1:5432/postgres`). Docker не нужен: global setup создаёт БД `orle_test`, применяет тонкий шим Supabase (`tests/db/supabase-shim.sql`: роли, `auth.users`, `auth.uid()`) и все миграции. Против настоящего Supabase: `TEST_DATABASE_URL=…:54322/postgres TEST_SUPABASE=1 pnpm test`. Каждый тест — транзакция с откатом; роли переключаются (`db.as.user(id)`, `anon`, `service`), серверное время фиксируется через `app_private.test_clock` (клиентам недоступна).

Что покрыто:

- **RLS и права** (`rls`, `grants`, `security`): нельзя начислить себе очки, голосовать за себя, отметить чужую привычку, отметить прошлый день, подделать время, сменить статус, вступить без инвайта, повысить себе роль. Чужие группы не видны. RLS включён на всех таблицах. У каждой SECURITY DEFINER-функции зафиксирован `search_path`. Права на функции сверяются с белым списком.
- **Очки** (`scoring`): стрики и потолок ×2, частичное выполнение, пропуски (в том числе до первой отметки), заморозки (дни и пропорциональное N), фейки (отзыв + штраф), переход месяца, неделя на стыке месяцев, смена часового пояса, повторный запуск крона, архивирование, перенос стрика при изменении привычки, сезоны и лидерборд.
- **Отметки и проверка** (`checkins`): досрочное одобрение, споры, взвешенные голоса против сговора, модерация, похожие и старые фото.
- **Группы и привычки**, **уведомления**, **достижения**, **«сегодня»**.
- **e2e**: вход по email-коду и SMS, онбординг, инвайт-ссылка, одобрение привычки, отметка с фото (проверяется, что выданное фото — WebP без EXIF), спор → отклонение → письмо автору через крон, PWA-файлы.

## Как считаются очки

Очки считает **только сервер**. Каждое событие — строка в `points_ledger`: тип, сумма, ссылки на привычку, отметку или период, причина и уникальный `idempotency_key`. Журнал **только пополняется**: UPDATE, DELETE и TRUNCATE блокирует триггер даже для суперпользователя. Исключение — каскад при удалении аккаунта или группы. Баланс — сумма журнала. Любой участник видит полный журнал любого другого.

Все коэффициенты — в [`config/scoring.ts`](config/scoring.ts) и в `groups.scoring_config` (их можно настроить для группы, изменения действуют со следующего дня). Тест `config-sync` падает, если SQL-дефолты разошлись с файлом.

| Событие | Формула (по умолчанию) |
|---|---|
| База периода | ежедневная 10 · еженедельная 30 · ежемесячная 100; × сложность 0,7/1/1,5; × 0,5 без фото |
| Отметка одобрена | база / N |
| Период выполнен полностью (N > 1) | + 20% базы |
| Бонус стрика | (очки периода + бонус) × (множитель − 1); множитель = min(1 + 0,1 × стрик, 2), стрик — включая этот период |
| Частично (≥ 1 отметки, < N) | очки за отметки остаются, без бонусов и штрафа, стрик = 0 |
| Пропуск (0 отметок) | − 50% базы, стрик = 0 |
| Фейк (отклонена проверкой или модератором) | отзыв начисленного за отметку + штраф 3 × (база / N) |
| Заморозка | замороженные дни пропорционально уменьшают N (с округлением); если N = 0 — без штрафа, стрик не меняется |

**Пример:** «Бег 3 раза в неделю», средняя сложность, фото, 4-я неделя подряд. 3 отметки × 10 = 30, бонус +6, множитель 1,4 → +14,4. Итого 50,4 за неделю.

**Закрытие периодов.** Тик (pg_cron каждые 5 минут) подводит период, когда в часовом поясе группы наступил следующий день, прошло grace-окно (по умолчанию 2 часа) и в периоде не осталось отметок на проверке. Пропущенные периоды тоже создаются и штрафуются, в том числе дни до первой отметки. Операция идемпотентна: повторный запуск ничего не начисляет. Тик обрабатывает до 2000 периодов за раз, остаток подберёт следующий.

**Изменение и удаление привычки** действуют только со следующего периода: текущий будет подведён как обычно, и избежать штрафа удалением не получится. Изменение проходит голосование и сохраняет стрик.

## Анти-чит

| Слой | Как реализовано |
|---|---|
| **1. Серверное время** | `create_checkin()` сам вычисляет локальный день по часовому поясу группы и ставит `created_at`. Клиент может лишь попросить засчитать «вчера», и только в grace-окно после полуночи. Отметок задним числом нет. |
| **2. Одна отметка на слот** | `unique (habit_id, period_start, slot)` и уникальная действующая отметка привычки за сутки — ограничения БД, а не UI. |
| **3. Пруфы** | Фото снимается в момент отметки (`capture="environment"`) и обрабатывается на сервере: EXIF и GPS удаляются (WebP), публичная версия лежит в приватном бакете и выдаётся участникам подписанными ссылками на 1 час. Время загрузки ставит сервер. Повтор изображения (dHash, расстояние Хэмминга ≤ 6 бит) и фото, снятое больше суток назад (по EXIF оригинала), помечаются флагом и попадают в аудит. Пруф регистрирует только сервер (`register_proof` доступна лишь service_role), и он одноразовый (≤ 15 мин). |
| **4. Проверка группой** | Отметка сначала `pending` в ленте. Её подтверждают или оспаривают (спор — только с комментарием). Сумма весов подтверждений ≥ 3 без споров → засчитано досрочно. Больше половины группы против → отклонено сразу. Иначе в конце окна (24 ч) решает перевес весов. За свои отметки голосовать нельзя. |
| **5. Защита от сговора** | Вес подтверждения = 1 / (1 + число подтверждений этого судьи этому автору за 30 дней): 1, ½, ⅓… Спор всегда весит 1. В группах меньше 3 человек — заметное предупреждение. |
| **6. Прозрачность** | Любой участник видит журнал очков, все отметки с пруфами, голоса с комментариями и заморозки любого другого. |
| **7. Rate limiting и аудит** | Отметки (5 в минуту), загрузки фото (10), комментарии (10), голоса (30). Лимит отметок пишет запись в `audit_log`, а не только отказывает. Панель модерации для owner/admin: подозрительные фото, частые отметки, споры, решения модераторов. Модератор может отклонить даже засчитанную отметку (кроме своей): очки отзываются, штраф ×3. |
| **8. Безопасность** | RLS на каждой таблице, клиент только читает, `search_path` зафиксирован во всех SECURITY DEFINER-функциях. CSP, HSTS, `frame-ancestors 'none'`, защита от open redirect, проверка подписи SMS-хука (Standard Webhooks), сравнение секрета крона за постоянное время. |

Что **не** защищено (честно):

- **Камера.** `capture` — лишь подсказка браузеру: на Android и iOS можно выбрать фото из галереи. Старое фото ловится по EXIF, но EXIF можно стереть. Новое постановочное фото сервер не отличит от настоящего — эту задачу решает только группа.
- **Сговор.** Убывающий вес делает сговор дорогим, но не невозможным: два друга в группе из трёх по-прежнему сильны. Поэтому для групп < 3 есть предупреждение.
- **Отметки без фото** — на честном слове, поэтому дают 50% очков.
- **Большие фото.** Фото больше 3,5 МБ уменьшаются в браузере (лимит тела запроса Vercel — 4,5 МБ), и у них теряется EXIF: проверка «старое фото» для них не работает, а повтор (pHash) — работает.

## Планировщик и уведомления

`app_private.tick()` по порядку: применяет отложенные настройки групп → решает отметки с истёкшим окном → подводит периоды → закрывает сезоны и открывает новые → ставит уведомления в очередь `notification_outbox` (с дедупликацией).

- **pg_cron** (основной путь): миграция 0600 сама регистрирует задачу `orle-tick` каждые 5 минут, если расширение включено (Supabase Dashboard → Database → Extensions → `pg_cron`). Если миграции применились до включения расширения, выполните `select cron.schedule('orle-tick', '*/5 * * * *', 'select app_private.tick()');`.
- **/api/cron/tick** выполняет тот же тик, удаляет неиспользованные фото из Storage и **рассылает уведомления** (web-push на все устройства + email). Его нужно вызывать по расписанию с заголовком `Authorization: Bearer $CRON_SECRET`:
  - Vercel Cron (`vercel.json`, раз в час; на тарифе Hobby Vercel разрешает только ежедневные задачи), или
  - любой внешний cron (например cron-job.org) каждые 5–15 минут, или
  - pg_cron + pg_net из самой БД:
    ```sql
    select cron.schedule('orle-notify', '*/10 * * * *', $$
      select net.http_get('https://<домен>/api/cron/tick', headers := jsonb_build_object('Authorization', 'Bearer <CRON_SECRET>'))
    $$);
    ```

Уведомления: **вечернее напоминание** (после выбранного времени по часовому поясу группы, если привычка не отмечена), **отметку оспорили**, **итоги недели** (понедельник после 9:00), **итоги сезона**. Пользователь включает и выключает каждое и выбирает каналы (пуш/email) в «Настройках». На iOS веб-пуш работает только для PWA, добавленного на экран «Домой» (iOS 16.4+).

## SMS-провайдер

Вход по email работает **без** SMS-провайдера. Чтобы включить вход по телефону:

1. Supabase Dashboard → Authentication → Providers → **Phone**: включить.
2. Authentication → **Hooks → Send SMS hook** → HTTPS: `https://<домен>/api/auth/sms-hook`. Сгенерированный секрет (`v1,whsec_…`) положить в `SEND_SMS_HOOK_SECRET`.
3. Выбрать провайдера в `.env`:
   - **Mobizon** (Казахстан/СНГ): `SMS_PROVIDER=mobizon`, `SMS_API_KEY`, при необходимости `SMS_SENDER` (согласованное имя отправителя) и `MOBIZON_API_HOST` (по умолчанию `api.mobizon.kz`).
   - **Twilio**: `SMS_PROVIDER=twilio`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `SMS_SENDER` (номер или Messaging Service SID `MG…`).
4. `NEXT_PUBLIC_SMS_ENABLED=true` — на экране входа появится вкладка «Телефон».

**Примерная стоимость** (проверьте перед запуском — цены меняются):

- **Twilio**: ≈ **$0,34** за SMS на номера Казахстана (официальная страница цен, могут добавляться сборы операторов) — около 170 ₸ за код.
- **Локальные SMS-шлюзы** (Mobizon и аналоги): по сторонним оценкам **~10–20 ₸** за внутреннюю SMS. Точный тариф смотрите в личном кабинете провайдера, для объёмов бывают скидки.
- Ориентир: 100 активных пользователей, которые входят по SMS раз в неделю, ≈ 400–450 SMS в месяц. Это ≈ 4–9 тыс. ₸ у локального шлюза или ≈ $150 у Twilio. Сессия живёт неделю и обновляется сама, повторный вход нужен редко. Привязав email в «Настройках», можно входить бесплатно.

Для разработки: `SMS_PROVIDER=dev` пишет SMS в `SMS_DEV_DIR` (в продакшене без явно заданной папки отключён).

## Деплой (Vercel + Supabase)

1. **Supabase**: создайте проект. Включите расширения `pg_cron` (и `pg_net`, если будете вызывать крон из БД). Затем:
   ```bash
   npx supabase link --project-ref <ref>
   npx supabase db push           # миграции 0100…0900
   ```
   Authentication → URL Configuration: Site URL `https://<домен>`, Redirect URLs `https://<домен>/auth/confirm`. Email Templates → Magic Link: вставьте содержимое `supabase/templates/magic_link.html` (там и код, и ссылка). Для продакшен-почты подключите свой SMTP (Settings → Auth → SMTP): встроенный SMTP Supabase сильно ограничен по количеству писем.
2. **Vercel**: импортируйте репозиторий, задайте переменные из таблицы выше (`NEXT_PUBLIC_SITE_URL` = ваш домен) и задеплойте. Крон из `vercel.json` подключится автоматически.
3. **Пуш**: `npx web-push generate-vapid-keys` → `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT=mailto:you@domain`.
4. **Email-уведомления**: ключ Resend и подтверждённый домен отправителя (`EMAIL_FROM`).
5. Проверьте: `curl -H "Authorization: Bearer $CRON_SECRET" https://<домен>/api/cron/tick`.

CI (`.github/workflows/ci.yml`): lint, typecheck, все тесты на Postgres 16, сборка.

## Производительность

`pnpm load-test 200 60` — синтетика: 200 групп × 8 участников × 4 привычки, 60 дней истории (6 400 привычек, 390 тыс. периодов, 290 тыс. отметок, 410 тыс. голосов, 280 тыс. записей журнала). Postgres 16 в контейнере разработки, медиана 5 прогонов, запросы — от имени участника с RLS:

| Запрос | Медиана, мс |
|---|---|
| `my_today()` — главная | 2,3 |
| `group_arena()` — арена | 5,5 |
| `leaderboard(week / all)` | 0,7 / 1,5 |
| лента: 20 отметок с голосами | 1,0 |
| журнал участника, 50 записей | 2,6 |
| тик: 4 800 решений + 6 400 периодов за ночь | ≈ 17 500 (≈ 2,7 мс на период) |
| повторный тик (нечего делать) | 410 |

По итогам замеров добавлены индексы (миграция 0900). Самый заметный — `points_ledger(checkin_id)`: без него закрытие периода сканировало весь журнал (231 с на тот же тик).

## Известные ограничения

- Полностью предотвратить обман нельзя (см. «Анти-чит»). Решающая защита — сама группа.
- Отклонение отметки после закрытия периода (модерация задним числом) отзывает очки и штрафует, но не пересчитывает уже начисленный стрик-бонус этого периода.
- Сезон один на группу; длительность меняется со следующего сезона.
- Казахский и английский интерфейсы заложены (`next-intl`, `profiles.locale`), но переводов пока нет.
- Вечернее напоминание приходит по часовому поясу группы, а не устройства.
- В локальном стеке без Docker нет Realtime.
